# نظام إدارة مصنع الذهب والمجوهرات والبيع بالجملة

نظام تشغيلي متكامل وليس واجهات شكلية. كل الشاشات متصلة بقاعدة بيانات PostgreSQL حقيقية، وكل حركة ذهب تُسجَّل داخل معاملة قاعدة بيانات آمنة في دفتر أوزان غير قابل للتعديل.

| الواجهة | المسار | المستخدم |
|---|---|---|
| لوحة المشرف (الأولوية الأولى) | `/sup` | المشرف، مدير الإنتاج |
| واجهة العامل (مصممة للجوال) | `/w` | العامل |
| لوحة الإدارة العامة | `/admin` | مدير النظام، المحاسب، مسؤول المخزون |
| متجر الجملة | `/store` | أصحاب محلات الذهب المعتمدون |

الواجهات الأربع تعمل على قاعدة بيانات واحدة، وتتحدث فوراً (PostgreSQL LISTEN/NOTIFY ← Server-Sent Events). الواجهة عربية بالكامل وتدعم RTL، وتعمل على الكمبيوتر والتابلت والجوال.

## التشغيل

### محلياً
المتطلبات: Node.js 20 أو أحدث، وPostgreSQL 14 أو أحدث.

```bash
cp .env.example .env            # عدّل DATABASE_URL و ADMIN_PASSWORD
npm run install:all
npm run build                   # بناء الواجهة
npm run migrate                 # إنشاء الجداول + حساب مدير النظام الأول
npm start                       # http://localhost:3000
```

للتطوير: شغّل `npm run dev:server` و`npm run dev:web` معاً (Vite على المنفذ 5173 مع توجيه `/api`).

### عبر Docker
```bash
DB_PASSWORD=... ADMIN_PASSWORD=... docker compose up -d --build
```

### بيانات تجريبية (اختياري، للتجربة فقط)
```bash
npm run seed:demo   # ينشئ مشرفاً و12 عاملاً ومحلاً وطلبات - كل الأسماء موسومة "تجريبي"
```
المستخدمون التجريبيون: `demo_sup`، و`demo_w1` إلى `demo_w12`، و`demo_shop`، و`demo_pm`، و`demo_acc`، و`demo_inv`. كلمة المرور لجميعهم: `Demo#2026`.

لا تشغّل هذا الأمر على قاعدة الإنتاج. التهيئة الأساسية لا تُدخل أي بيانات تشغيلية وهمية، وتبدأ نسب العجز كلها بصفر.

   - إرسال التصميم للعميل واعتماده، مع التحقق من منع الصب قبل الاعتماد.
   - تسجيل 100 جم على الطلب، وتسليمها للعامل الأول مع توقيعه.
   - مرحلة الصب: بدء العمل وإيقافه بسبب ثم استئنافه.
   - إرجاع 99.7 جم. يحسب النظام عجزاً فعلياً 0.300، منها 0.200 طبيعي و0.100 غير طبيعي.
   - إلزام تسجيل السبب، ثم الإحالة للتحقيق، ثم تسجيل نتيجة التحقيق مع استرداد جزء من العجز.
   - إقفال العهدة، والانتقال التلقائي إلى العامل التالي، ثم إكمال بقية المراحل.
   - تسجيل الوزن النهائي، وإصدار فاتورة أجور فقط (الوزن × الأجرة + الضريبة).
   - ظهور الحالة للعميل دون أي معلومات داخلية، ثم التسليم وإقفال الطلب.
   - التحقق من المعادلة: 100 = المسلَّم + البقايا + المسترد + العجز الطبيعي + غير الطبيعي.
2. **العمليات الجماعية:** تسليم واستلام 3 طلبات في جلسة واحدة، كل طلب بحركة مستقلة، مع كشف للطباعة.
3. **منع تكرار تسجيل الوزن:** على مستوى قاعدة البيانات، ومنع الإرسال المزدوج بمفتاح العملية.
4. **منع التعديل الصامت:** محاولات UPDATE وDELETE المباشرة على الدفاتر تُرفض. التصحيح يتم بحركة عكسية مع السبب والمستخدم والتاريخ.
5. **40 عاملاً بالتزامن:** تسليم واستلام متوازٍ دون تضارب ودون تجاوز رصيد الخزنة.
6. **مطابقة إجمالي الذهب:** الخزنة + العهد + الطلبات + البقايا + الفقد + المسلَّم = صافي الوارد.
7. **الصلاحيات:** مصفوفة صلاحيات لكل نوع مستخدم، ومسح QR لطلب غير مسند إلى العامل، ومنع صلاحية عن مستخدم بعينه.
8. **المتجر:** منتجات، وسلة، وأجور خاصة بالعميل، ورفض العيار غير المتاح.

## نموذج العهدة ومحاسبة الأوزان

كل جرام له موقع واحد معروف في أي لحظة. دفتر `gold_ledger` يعمل كقيد مزدوج للوزن: كل حركة تنقل وزناً من موقع إلى آخر لمادة واحدة (عيار + لون)، ومرتبطة برقم الطلب والعهدة والمرحلة والعامل.

| الموقع | المعنى |
|---|---|
| `vault` | الذهب في المخزون (الخزنة) |
| `order` | ذهب تحت التشغيل مخصص لطلب، وليس مع عامل |
| `worker` | الذهب الموجود فعلياً مع العامل (العهدة) |
| `scrap` | بقايا قابلة للاسترداد وإعادة الاستخدام |
| `loss_normal` / `loss_abnormal` | العجز الطبيعي، والعجز غير الطبيعي المعتمد |
| `loss_suspense` | عجز غير طبيعي تحت المراجعة |
| `finished` / `delivered` | منتجات جاهزة في المخزون / مسلَّمة للعملاء |
| `external` / `variance` | دخول وخروج من المصنع / فروقات جرد وتحويل موثقة |

**عند الاستلام** (دالة `calc_loss` في قاعدة البيانات، بأرقام عشرية دقيقة):

```
العجز الفعلي          = الوزن المستلم − الوزن المرتجع − البقايا المستردة
العجز الطبيعي المسموح = الوزن المستلم × نسبة المرحلة (اللقطة المحفوظة لحظة التسليم)
العجز غير الطبيعي     = max(0, العجز الفعلي − العجز الطبيعي المسموح)
```

قيد قاعدة البيانات يضمن المعادلة التالية في كل تسوية:
`الوزن المستلم = المرتجع + البقايا + الفقد المسجل`

### قواعد الرقابة

**الأوزان والمواد**
- تُخزَّن الأوزان بدقة 4 خانات عشرية. دقة العرض 3 أو 4 خانات حسب الإعدادات.
- لكل عيار ولون رصيد مستقل. التحويل بين مادتين يتم بحركة موثقة تتطلب صلاحية اعتماد.
- القطع التي فيها أحجار: يُخصم وزن الأحجار المركبة (1 قيراط = 0.2 جم) تلقائياً للوصول إلى صافي الذهب.

**نسب العجز**
- نسبة كل مرحلة تُحفظ كلقطة داخل العهدة عند التسليم، فلا تتغير بأثر رجعي.
- كل تغيير للنسبة يُسجَّل كصف جديد مع التاريخ واسم المدير.

**المراجعة**
- العجز غير الطبيعي يتطلب سبباً، ويُحال للمراجعة والاعتماد قبل إغلاق التسوية.
- لا يعني العجز غير الطبيعي تلقائياً مسؤولية العامل. المسؤولية تُحدَّد فقط بنتيجة التحقيق.

**منع التعديل**
- مشغلات (triggers) قاعدة البيانات تمنع تعديل أو حذف الحركات والتسويات والفواتير الصادرة وسجل التدقيق.
- التصحيح يتم بحركة عكسية مع السبب والمستخدم والتاريخ.

| التدقيق | `audit_log` غير قابل للتعديل، لكل إنشاء وتعديل وحذف وتصحيح واعتماد، مع تصدير Excel |

## الأمان

- **الجلسات:** ملفات تعريف ارتباط `httpOnly` و`SameSite=Strict`، وتُخزَّن مشفرة بـ SHA-256 في قاعدة البيانات.
- **كلمات المرور:** مشفرة بـ bcrypt، مع حماية من محاولات التخمين.
- **الصلاحيات:** تُفحص على الخادم في كل نقطة API. يمكن تخصيصها لكل دور، وإضافة صلاحية أو منعها لمستخدم محدد.
- **قاعدة البيانات:**
  - مشغلات منع التعديل.
  - سكربت `server/sql/app_role.sql` لمستخدم تطبيق محدود لا يستطيع تعديل الدفاتر أو حذفها.
  - أقفال صفوف وأقفال استشارية لمنع تجاوز الأرصدة عند التزامن.
  - إعادة محاولة تلقائية عند تعارض المعاملات.
- **المفاتيح السرية:** في متغيرات البيئة على الخادم فقط، وليس في الواجهة الأمامية أبداً.
- **الملفات المرفوعة:** تُقدَّم عبر فحص صلاحية مرتبط بالكيان؛ العميل يرى ملفات طلباته الظاهرة له فقط.
- **النسخ الاحتياطي:** `scripts/backup.sh` (يستخدم `pg_dump` ويضغط الملفات المرفوعة مع حذف النسخ القديمة)، وفيه تعليمات الجدولة والاسترجاع.

## ما يحتاج إعداداً خارجياً أو تطويراً لاحقاً (بوضوح)

- **الفوترة الإلكترونية – المرحلة الثانية (الربط مع منصة فاتورة):** النظام يولّد كل البيانات المطلوبة (QR بصيغة TLV، وUUID، وICV، وسلسلة hash، وUBL XML). لكن الإرسال الفعلي للهيئة والتوقيع التشفيري (CSID/شهادة ECDSA) يتطلبان تسجيل المنشأة في منصة "فاتورة" والحصول على الشهادة. هذه خطوة تكامل يجب تنفيذها بعد التسجيل، ولم تُنفَّذ هنا.
- **WhatsApp / SMS / البريد:** المحوّلات جاهزة، لكنها لا ترسل شيئاً قبل ضبط بيانات المزود في متغيرات البيئة. بدونها تُعلَّم الرسائل "skipped".
- **التخزين السحابي:** الملفات تُحفظ حالياً على قرص الخادم (`UPLOAD_DIR`، ومجلد Docker دائم) مع نسخ احتياطي. الربط مع S3 أو ما يشابهه يتطلب إضافة محوّل تخزين في `server/src/lib/uploads.js`.
- **PDF:** الفواتير والكشوف تُطبع أو تُحفظ PDF من المتصفح بتنسيق طباعة مخصص. Excel يُصدَّر كملف xlsx حقيقي.
- **الحذف:** حذف الموظف المرتبط بحركات يتحول إلى تعطيل حفاظاً على السجل التاريخي. حذف مرحلة مستخدمة سابقاً يجعلها غير فعالة بدلاً من إزالتها.
- **ما بعد النشر:** يُنصح باختبار الأداء على الأجهزة الفعلية للمصنع (الموازين وقارئات الباركود) قبل التشغيل الكامل.
